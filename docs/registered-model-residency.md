# 正式闭环的模型常驻规则登记与审计

2026-10-23。新增可选的 `execution.settings.model_residency`，用于在正式冻结前明确M6/M7的模型装载规则。当前开发重跑固定使用bb168cd0，本次不修改其源码或设置，不改任务、提示、训练量、角色权重、token预算或修复策略。正式训练0/6。

| 设置 | 行为 | 交互清单版本 |
| --- | --- | --- |
| 不设置或 `cold-task-v1` | 原有逐任务释放、角色路径变化时重载 | 1 |
| `shared-condition-v1` | 每条件从冷权重开始；条件内仅复用一个底座及分析适配器，任务之间重置账本和记录；条件结束释放 | 2 |

未知值或非字符串拒绝。新规则统一作用于P1–P4和六项M7条件，不能逐条件选择性启用。实际执行角色继续禁用分析适配器，分析角色启用适配器；各自tokenizer/EOS和共享硬预算规则见[底座开发验证](shared-base-residency-development.md)。正式路径只接受已绑定、可安全共享的匹配base/LoRA，资格不符时在创建交互尝试前报错，不能静默改回重载；注入池仍仅限明确标记的工程协议。

任务间复用权重，不复用工具状态、提示/答案或已生成的KV信息。每任务仍有独立49152-token共享账本，失败预留计费和上下文硬拒绝保留。独立硬检查、动态k及训练调度不改变；M5诊断与损失评测的装载规则不受这项M6/M7设置影响。

每任务快照增加 `resident_at_task_start`，保留角色模型身份、实际加载状态/耗时和当前任务账本。交互核验逐条件从未驻留状态审计：第一条不得从上一条件继承模型，驻留后不得在条件内部暗中重载；加载角色/路径与快照一致。条件总时长必须覆盖真实加载时间，各条件时长之和不得大于全阶段总时长。错误、超限及所有任务记录保留，GpuBusy仍先写入并flush事故行再使整个实验失败，不能因为缓存路径而重新计入方法效果。

每条件的时间明确包含装载、所有任务及释放；全阶段时间另包含入口核验等开销。任务原始耗时保留，但首任务承担冷加载，后续为权重复用，不能把它们当作同样冷启动的独立时间样本。时间效率按完整条件总耗时描述，不据这项工程调整追加确认性显著性检验或改变RQ3的固定token预算主指标。

四项新增工程检查使用相同公开规格的合成任务和注入池，验证M6四次/M7六次条件加载与释放、任务内预算重新开始、冷/常驻的执行轨迹和成本计数一致、M6及M7的分离揭晓/评分入口均可核验。另拒绝重新计算seal后伪造的条件预热、额外重载、缺失计时、遗漏加载成本、错误策略与遗漏总耗时；注入GPU资源事故时保存一条记录并释放权重。不把这些夹具称为真实9B任务成功结果。

本地286项检查含16项可选ML跳过，其余通过；服务器独立CPU快照全部286项通过、无跳过，日志139.448秒。随后仅扩展测试以覆盖M7揭晓/评分，生产三文件保持不变，服务器4项针对性检查通过。原始全量快照哈希和最终测试文件哈希分别保留在[证据目录](../examples/results/formal-m3ab-residency-registration/README.md)。检查期间GPU源bb168cd0保持干净且不变，没有观察到新的资源事故文件。
