# 实验规划指南：基于误差曲线的学习率调整与证据驱动纠偏

日期：2026-10-20

状态：研究实验设计。2026-10-21 已补充离线工具链、规则分析、轻量训练、微型因果语言模型与 LoRA 的 CPU 训练和完整断点恢复；QLoRA 代码入口已提供，但尚未在目标显卡验证，也未开展完整四组研究消融和独立确认性测试。实际实现范围见[实现与复现指南](implementation-guide.md)及[神经模型训练指南](neural-training.md)。

关联文档：[研究建议报告](agent-intent-fidelity-research-proposal.md) · [稳定成果产出方案](agent-error-analysis-stable-output-plan.md)

## 1. 本轮方案改进

用户提出根据误差曲线动态调整学习率和调节率，以减小损失。本指南将其落实为两个相互分离、可独立检验的控制过程：

1. **训练阶段：** 根据固定验证集的误差，调整误差分析模型的学习率。
2. **执行阶段：** 冻结模型参数，根据当前任务的证据、违规状态和修复退化情况选择纠偏动作。

这里将“调节率”操作化为纠偏范围、验证动作与修复尝试的选择，不假定存在一个天然有效的连续控制系数。若后续特指 LoRA 的 `lora_alpha` 或损失权重，应另建实验，不与本轮自适应机制混在一起。

核心改进包括：

| 原始想法中的不确定点 | 本指南的处理 |
| --- | --- |
| 根据哪个误差调参 | 学习率用固定验证损失；纠偏用逐项执行证据 |
| 曲线波动就调整 | 固定评估时点、改善阈值、耐心窗口和冷却期 |
| 误差大就增强纠偏 | 先区分真实违规、证据不足和检查器误报 |
| 同时调整很多参数 | 固定模型、LoRA 缩放和损失权重，仅比较两个明确因素 |
| 损失下降即认为成功 | 最终以独立测试的合规任务成功率、退化和成本判断 |
| 动态策略不断学习测试集 | 策略在开发集确定；测试时只允许预先规定的任务内响应 |

本指南不保证损失单调下降，不保证动态策略优于预设调度，也不保证缩短训练时间。学习率平台调度和早停已有成熟实现，不单独作为研究新颖性。[1][2]

## 2. 研究问题与预先声明的假设

- **H1：** 相比相同预算的预热加余弦衰减，验证集平台触发的学习率调整能改善分析器在未见任务上的诊断质量。
- **H2：** 相比固定纠偏规则，证据驱动的任务内动态纠偏能提高合规任务成功率，并减少修复退化。
- **H3：** 两者组合的收益不是仅由更多训练 token、更多候选修复或更高检查成本带来。

H1、H2 可能独立成立或不成立。即使验证损失更低，若实际诊断和闭环行为没有改善，也不能宣称任务级假设成立。主比较、实用效应门槛、预算与统计方法在独立测试前冻结。

## 3. 数据隔离与误差信号

### 3.1 数据用途

| 数据 | 可用于什么 | 不可用于什么 |
| --- | --- | --- |
| 训练集 | 梯度更新、构造监督输出 | 最终泛化结论 |
| 训练验证集 | 调度学习率、选择检查点 | 声称完全独立测试表现 |
| 策略开发集 | 选择纠偏规则、阈值和控制窗口 | 最终确认性结论 |
| 独立测试集 | 冻结方案后的最终评价 | 回传梯度、调整阈值或选择超参数 |

按基础任务、模板和来源划分，不能仅随机拆分同一轨迹的多个视图。验证集与测试集不进入训练 packing；受控变异和自然轨迹单独标识。若资源有限合并两个开发用途，应明确承认开发集被反复使用，并保留新的独立测试任务。

前序方案的 40 个先导任务、160 条诊断轨迹与最多 320 个证据视图属于开发和评估资产，不自动等同于足够的独立训练样本。新增训练数据须另行核验和隔离。

### 3.2 三类曲线

| 曲线 | 计算与解释 | 控制用途 |
| --- | --- | --- |
| 训练与验证损失 | 固定监督目标下的 token 负对数似然 | 学习率调度、检查点选择 |
| 诊断误差 | 漏报、误报、错误放心、待判定及覆盖 | 判断分析器是否学到有效能力 |
| 执行表现 | 合规任务成功率、修复退化率、成本 | 纠偏策略的开发与最终验证 |

验证损失按参与损失计算的非 padding token 汇总，保持标注模板、掩码和聚合规则一致；不能简单平均不同长度 batch 的均值。训练与验证损失仅在目标和归一化口径一致时直接比较。

可额外绘制按任务或错误类型的宏平均指标，避免长轨迹和高频类型掩盖其他错误。平滑曲线用于显示，第一版调度器使用完整固定验证集的原始聚合值，不同时叠加多个未经检验的平滑控制器。

## 4. 训练目标与固定参数

### 4.1 第一版训练任务

使用已有约 3B 参数模型进行 QLoRA 监督微调。输入为原始要求、当前要求表、工具记录与环境证据；输出为结构化诊断：要求 ID、状态、错误类型、证据引用及可执行修复建议。

第一版采用固定的监督 token 损失，不新增复杂多头结构，不动态改变不同损失项的权重。实际执行违规率通常不可直接求梯度，不能简单加进 token 损失就认为能够反向传播。后续如引入分类头、偏好学习或强化学习，另行定义训练目标和成本。

### 4.2 建议起点

以下为探索性起点，不是经过本项目验证的最优参数：

| 项目 | 初始建议 |
| --- | --- |
| 模型 | 固定一个约 3B 的开源基础或指令模型，记录精确版本 |
| 微调 | 4-bit QLoRA，兼容的 BF16 计算配置 |
| LoRA | `r=16`、`lora_alpha=32`；各组固定目标模块和 dropout |
| 优化器 | AdamW，权重衰减及其他参数预先固定 |
| 峰值学习率 | 先比较 `5e-5`、`1e-4`，开发阶段确定共同起点 |
| 预热 | 最大计划优化器更新步数的 5% |
| 最低学习率 | 候选起点 `5e-6`，两种调度采用相同下界 |
| 梯度裁剪 | 最大梯度范数候选值 1.0，记录裁剪前范数 |
| 最大训练量 | 候选上限 3 个 epoch，最终依开发实验冻结 |
| 数据长度 | 实测分布；候选最大长度 4096，不截掉关键要求或标注 |

普通 LoRA 的缩放与 `alpha/r` 有关，rsLoRA 等变体采用不同缩放规则。改变 alpha 会改变适配器贡献，不能将它当作与学习率完全等价的参数。[3] 本轮固定 alpha、rank 和训练损失，避免归因混乱。

## 5. 学习率控制的具体规划

### 5.1 两种调度

- **L0：预热加余弦衰减。** 预先固定峰值、最低值与最大训练步数，不根据验证集改变曲线。
- **L1：预热加平台触发衰减。** 预热后维持当前学习率，固定验证损失持续没有实质改善时降低学习率。

L0 是主动降低学习率的强基线，不能只和恒定的大步长比较。两者使用相同初始化、样本顺序、预热、峰值候选、最大训练 token 和评估频率。

### 5.2 L1 的起始配置

可采用 PyTorch `ReduceLROnPlateau` 的以下候选配置，正式运行时以锁定版本的行为为准：[1]

```yaml
mode: min
factor: 0.5
patience: 2
threshold: 0.001
threshold_mode: rel
cooldown: 1
min_lr: 0.000005
```

- 首次完整验证建立参考值；相对历史最好损失下降超过 0.1% 才视作实质改善。
- `patience=2` 在该实现语义下，通常在坏评估次数超过 2 时触发降低，而不是恰好第 2 次。不能将它写成两个 epoch。
- 调度器只在预热结束后的固定验证事件调用一次；梯度累积的微批次不单独触发。
- 降低后冷却 1 个评估事件，减少连续触发；不能误解为 1 个训练 step。
- 预热与平台调度需按训练阶段明确切换，避免两个调度器同时修改同一学习率。

阈值 0.1% 是待验证的候选值。如果验证数据波动明显大于它，应在开发阶段调整，并为所有正式运行冻结规则，不能在测试时按结果修改。

### 5.3 评估频率

初始建议约每 0.1 个 epoch 做一次完整训练验证，并转换为固定优化器更新步间隔。两种调度采用相同频率、验证数据与损失汇总方式。若评估成本过高，可在开发阶段统一降低频率，不应只给动态组额外观察机会。

较贵的执行级开发评测可按每个 epoch 或预先选定的少数检查点进行。最终测试只评选定检查点，不能用测试成绩挑选训练步数。

### 5.4 早停、恢复与异常

探索阶段可启用早停，候选为连续 6 个验证事件无实质改善，且最近一次降低学习率后已完成至少 2 个验证事件。两种调度采用相同早停原则，检查点选择以预先约定的验证指标为准。[2]

正式实验建议区分两种口径：

1. **相同训练量比较：** 使用同一最大 token 预算，主实验不因普通平台期提前结束；数值异常仍须停止。用于隔离调度本身的质量差异。
2. **效率比较：** 两组按相同预先定义的早停策略停止，比较实际 token、总 GPU 时间及最终质量。提前停止不自动等于算法更优。

NaN、Inf、持续异常梯度或 OOM 应记录为异常并按协议处理，不能把这种中断当作成功早停。恢复训练时同时恢复模型、优化器、调度器、随机状态及数据进度。若从较早检查点回退并分支重训，应计入额外计算，不混入未回退的主比较。

## 6. 将调节率改进为可解释的动态纠偏规则

### 6.1 定义控制动作

不使用难以解释的“力度为 0.7”。第一版采用离散动作：

- `VERIFY`：追加证据，不改变交付物。
- `LOCAL_REPAIR`：针对一个明确违规对象进行局部修复。
- `GROUP_REPAIR`：针对已确认存在依赖的要求组修复。
- `REJECT`：拒绝造成退化或新增硬约束违反的候选。
- `STOP`：预算耗尽、无可接受候选或证据不足且无法继续验证。

局部与组修复的对象和允许路径通过工具或补丁接口定义，不只依赖提示词声称“局部修改”。组修复不能扩大工具权限或越过原有硬约束。

### 6.2 证据驱动的状态转换

| 当前观测 | 动作与限制 |
| --- | --- |
| 证据不足 | 优先 VERIFY；追加验证预算耗尽则保留待判定 |
| 确认单项违规 | LOCAL_REPAIR，生成隔离候选 |
| 局部修复失败，且证据确认要求之间有依赖 | 在原有预算内考虑 GROUP_REPAIR |
| 候选产生新硬约束违反或破坏受保护要求 | REJECT；不得仅因综合分更高而接受 |
| 候选满足目标并通过保持检查 | 提交候选，更新要求和证据记录 |
| 失败原因仍不明确 | 补证或 STOP，不自动增强修复力度 |

禁止仅凭“本次误差比上次大”就扩大修改范围。候选之间的错误差异可能来自检查器噪声，必须依据原文与真实证据。

### 6.3 固定与动态对照

- **R0：固定策略。** 按固定顺序处理已确认的违规，每次局部修复一个目标；相同的证据不足处理和候选接受检查仍然执行。
- **R1：动态策略。** 按预先规定的证据状态选择局部或组修复，并允许补证后改变下一步动作。

两组保留相同硬约束、工具权限、候选接受规则、最大模型 token 和检查预算。R0 不能故意去掉安全检查来制造动态策略优势。

探索性上限可设为每任务最多 3 个候选修复、最多 2 次追加验证。两组上限相同，所有调用计费；最终额度需在开发阶段冻结。运行级历史违规不可被后续恢复抹除。

### 6.4 模型与控制器分离

执行实验中冻结误差分析模型参数。R1 可以根据当前任务的真实反馈选择预先定义的动作，但不能根据测试集累计成功率修改规则、学习率或模型权重。

这与训练时的学习率调度是两个阶段，不形成一边执行测试、一边回传测试奖励更新模型的混合流程。后续在线学习若另行研究，应单独定义数据授权、评测和预算协议。

## 7. 实验矩阵与单卡计算安排

### 7.1 四个组合

| 组别 | 训练调度 | 冻结模型后的执行策略 |
| --- | --- | --- |
| A | L0：预热加余弦 | R0：固定纠偏 |
| B | L1：预热加平台 | R0：固定纠偏 |
| C | L0：预热加余弦 | R1：动态纠偏 |
| D | L1：预热加平台 | R1：动态纠偏 |

至少记录分析器本身的离线诊断与执行闭环的在线结果。B-A 与 D-C 衡量学习率策略差异，C-A 与 D-B 衡量纠偏策略差异。差异之差可用于探索交互作用，但小样本不足时不能宣称两种机制存在协同。

### 7.2 训练复用

若使用 3 个训练随机种子，只需训练 2 种调度 × 3 种子 = 6 个模型检查点；每个检查点再分别评估 R0 和 R1。不能为四组重复训练完全相同的模型。

如果开发阶段同时比较两个峰值学习率，则完整开发网格是 2 种调度 × 2 个峰值 × 3 种子 = 12 次训练。正式比较可使用开发阶段选定的共同峰值来隔离调度差异；若各策略分别调优，则明确为调优后系统比较，并匹配搜索预算。

### 7.3 与前序 320 次先导运行的关系

原有 40 任务 × 4 组 × 2 重复 = 320 次先导用于无新增训练前的机制开发，不应误算成本轮完整训练实验。

本轮如仍使用 40 个开发任务、2 次执行重复，完整矩阵为：

```text
2 种训练调度 × 3 个训练种子 × 2 种执行策略
× 40 个任务 × 2 次执行重复 = 960 次执行评估
```

它们包含 6 次训练和 960 次任务运行；不含数据制作、额外调参和正式新测试任务。先导任务已经用于开发时，不能重新命名为独立测试集。

### 7.4 单张 RTX 5090 的时间预算

以前述 3B、5,000 条样本、平均输入输出合计 2,000 token、3 个 epoch 为例，训练总量为 3,000 万 token。若实测有效吞吐在 500–1,500 token/s，则纯训练约 5.6–16.7 小时；加约 20% 的常规开销后，规划值约 7–20 小时/次。

这是待测速校准的假设，不是 RTX 5090 实测基准，也不是时长承诺。动态组如频繁进行昂贵执行评估，额外开销应单独计算。6 次训练约 42–120 GPU 小时，12 次约 84–240 GPU 小时；960 次执行评估另算，不能据此承诺整个项目几天完成。

开始前用最终模型、长度分布、batch、梯度累积和评估配置进行短跑；排除编译预热后记录稳定吞吐与峰值显存。单卡优先串行安排训练和模型执行，冻结并记录软件、驱动及硬件配置。

## 8. 监测、日志与结果表

### 8.1 最低日志

| 范围 | 必须记录 |
| --- | --- |
| 训练 | run ID、数据版本、种子、更新步数、已见 token、损失、学习率、梯度范数 |
| 调度事件 | 监测指标、最好值、坏事件计数、冷却状态、降学习率前后值 |
| 检查点 | 模型与优化器状态、选择指标、选择理由、验证时间 |
| 执行控制 | task ID、模型检查点、证据、动作、修复范围、剩余预算 |
| 修复 | 原已满足项、修好项、新破坏项、接受或拒绝及原因 |
| 成本 | 训练与验证 GPU 时间、推理 token、工具与检查调用、总延迟 |

### 8.2 指标与图表

主指标为独立测试的合规任务成功率。辅助指标为分析器漏报与误报、错误放心、修复成功率、修复退化率、待判定比例及成本。

至少输出以下图表：

1. token 进度对训练和验证损失，标注学习率调整事件。
2. token 进度对学习率与梯度范数，保留原始曲线。
3. 检查点对诊断误差，展示损失与实际能力是否一致。
4. 各组合的合规成功、退化与成本，包含任务聚类的不确定性区间。
5. 实际 GPU 时间对验证质量，用于效率比较。

不同调度、种子曲线不能只挑最好的一条；报告全部运行及汇总。按基础任务处理重复与变异相关性，训练种子单独显示；只有 3 个训练种子时，应承认跨训练波动估计有限，不能把大量执行重复当成大量独立训练。

| 观察结果 | 合理解释与下一步 |
| --- | --- |
| L1 验证损失更低，诊断和执行指标不变 | 优化收益未转化为任务收益，检查目标对齐 |
| R1 减少退化但大量停滞 | 报告成本与完成率权衡，不能只报告退化下降 |
| D 优于 A，但单因素无明显差异 | 先报告不确定性，不直接宣称协同机制 |
| 固定策略表现相当且更便宜 | 保留简单方案，报告复杂机制必要性未获支持 |
| 平台调度频繁触发且结果波动大 | 检查验证噪声、窗口和数据覆盖，仅在开发阶段调整 |
| 多次训练均不如未微调模型 | 检查数据质量、遗忘和标注偏差，保留未微调基线 |

最低验收内容是完整配置、无泄漏数据划分、可恢复训练状态、可核验控制事件、独立指标与完整成本，不要求正向结果。

建议执行顺序：先核验任务和标签，再跑单种子的 L0 与 L1，然后冻结模型比较 R0 与 R1；通过日志和边界检查后扩展到完整种子矩阵，最后开展新的独立测试。自动调参前，先验证调度器在预设验证序列上的触发、冷却、最低学习率和断点恢复行为。

## 10. 正式实验前检查清单

- [ ] 基础任务分组及训练、验证、策略开发、测试用途已冻结。
- [ ] 验证损失的标签、掩码、token 归一化和聚合口径一致。
- [ ] 两种调度的预热、峰值、下界、评估频率及预算可比。
- [ ] 平台调度只在正确阶段调用，耐心与冷却以评估事件计数。
- [ ] 已区分相同训练量比较与早停效率比较。
- [ ] LoRA alpha、rank、损失权重和评分口径固定。
- [ ] R0、R1 共享权限、硬约束、接受规则和最大预算。
- [ ] 测试时模型冻结，动态动作仅依当前任务证据触发。
- [ ] 所有验证和推理开销计入成本，失败与中断保留。
- [ ] 主比较、实用效应门槛和不确定性分析事先确定。
- [ ] 已加入未微调模型和简单提醒作为适用的外部参照。
- [ ] 没有将本指南中的设计或时间假设描述为已完成实验。
