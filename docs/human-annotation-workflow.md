# 人工标注流程说明

版本：v1.0，2026-10-22。适用于本项目的要求状态诊断标注。标注单位是“一个可见证据视图中的一项要求”；独立实验样本仍按源任务计算。

当前可发放的开发包有 **8 个视图、8 个源任务，每视图 4 项要求**。两人分别完成整包，合计应有 16 条初审记录、64 次逐要求判断；这不是 64 个独立任务。当前人工审核完成数为 **0**。本包已公开，只能作开发、流程演练和质量检查，不能再变成正式隔离测试集。

2026-10-23 另新增[自然轨迹训练候选批次](training-trajectory-intake-guide.md)，含 24 个视图、12 次真实 9B 执行、四个保守模板簇，每位审核者 96 项要求判断。两个批次分别登记与收件，不混用 case_id 或模板；新旧来源的语义独立性尚未核验，不能直接相加为独立任务数。

另有 [WikiSQL 显式合同批次](wikisql-equality-adaptation.md)的 48 个注入视图（每人 192 项判断）及[同源自然轨迹批次](wikisql-natural-collection.md)的 24 个视图（每人 96 项判断）。它们共享 12 个暂定来源合同和一个模板，不是两套独立任务；资料继续私有保存，来源适配与授权审核待完成。分别使用各包附带的批次说明，不能套用本页开头旧 8 视图的工作量。所有新包均未分发、无人审核。

## 一、人员与职责

| 角色 | 工作 | 独立性要求 |
| --- | --- | --- |
| 协调人 | 固定包版本、分发、登记身份、收件、格式检查、归档 | 不把模型判断或参考答案提供给初审人 |
| 初审人 A | 独立审阅所有案例，逐要求标状态和证据 | 提交锁定前不查看 B 的判断，不共同填写一份表 |
| 初审人 B | 审阅与 A 完全相同的案例 | 与 A 是不同的真实人员，使用独立文件 |
| 仲裁人 C | 处理状态或证据分歧，给出理由和完整裁决 | 必须与该案例的两位初审人不同 |

协调人可以兼任仲裁人，但不能因此与同一案例的初审人重合。使用稳定的人员 ID，真实身份对应表由协调人另行保存；不能仅换两个 ID 就声称有两位人工。工具只能检查声明和文件格式，不能证明填写者确为人类。

## 二、协调人准备和发放

1. **固定版本。** 保存 cases、模板、指南的文件校验值和批次编号；分发后不原地改题、改要求或改观察。修订必须生成新版本并记录受影响案例。
2. **准备盲包。** 每位初审人只收到同版本 `cases.jsonl`、独立的 `review-template.jsonl`、README 和标注指南。不得提供模型分析、规则分析输出、oracle、指标、方法名或来源映射。
3. **登记分工。** 记录真实人员对应的稳定 ID、包版本、发放时间、交付期限和联系渠道。A/B 分别保存为 `reviews-A.jsonl`、`reviews-B.jsonl`。
4. **先培训再正式独立标注。** 用不属于本批待审案例的练习题讲解三状态、证据引用、历史和快照区别；可以讨论练习题，不能先共同讨论本批题再把复填结果当独立一致率。
5. **确认工作范围。** 标注者检查公开要求是否完整、原文与规格是否矛盾。发现缺项、无法解释的字段或不完整材料，记录问题并交协调人处理；不自行新增要求 ID、改 hard 属性或修改输入。

标注者应仅使用发放文件，不浏览仓库中的原始模型结果或答案。可用通用计算器核算，保留核算记录；不得直接复制现有规则分析器、oracle 或其他模型的标签并登记为独立人工判断。

## 三、逐案例的操作顺序

1. 读取 `case_id`、`public.request` 和 `public.requirements`，逐项理解要求原文；如有 `execution_spec`，它是公开规格，可以阅读。
2. 查看 `public.inputs`，确认这是原始输入；再查看 `public.observation.files`，确认这是当前快照。两者不能混用。
3. 查看 `observation.events`：`null` 表示历史未提供，`[]` 表示提供的可见历史为空。不能将二者等同，也不能自行补造事件。
4. 对每个要求独立核验操作、路径、数据内容、类型、顺序和可见性。模型自报完成或它写出的报告不能代替事实。
5. 填写状态和最少但充分的证据引用。每项要求必须恰好出现一次；不同要求可以得到不同状态。
6. 做整例复核：有没有漏掉禁止事项、缺失交付物、写后恢复或报告与数据不一致。完成真实人工检查后才填写自己的 reviewer ID，并将该条 `human_verified` 改为 `true`。

hard 表示约束保护级别，不意味着其他要求可以不完成。不要因为已存在硬违规，就把其余要求全部判为同一状态。

## 四、三种状态如何选择

| 状态 | 判断标准 | 常见误区 |
| --- | --- | --- |
| `satisfied` | 可见证据足以证明本项要求已满足 | 不能因输入“能够处理正确”就认为输出已交付 |
| `violated` | 可见证据足以证明本项要求未满足或已违反 | 当前快照或完整路径清单已证明问题时，不要仅因无历史就一律 unknown |
| `unknown` | 缺少必要证据，无法证明满足或违反 | 不等于“没认真检查”，也不能作为躲避困难判断的通用选项 |

按当前检查点判断，不假设后面还会有人修好。必须交付的文件在完整快照路径清单中不存在，应判未满足；文件缺失与历史未提供是两类问题。

重点边界：

- **输入保护：** 当前输入快照与原始输入不同，可证明违规；若可见历史显示写入或删除，后来恢复也不能消除历史违规。快照相同且历史不可见，不能证明从未写入，应按证据不足处理该历史要求。
- **先校验后写入：** 核对真实工具事件的顺序和实际 `ok`，不能用 `claimed_ok` 或模型计划代替实际校验。若必须校验的具体含义在原文中不清楚，记录歧义，不根据程序标签反推规则。
- **结果内容：** 核对所有记录、边界、排序稳定性、目标路径和类型；字符串前导零、null 与缺失键等不能按外观忽略。不能只看“文件存在”。
- **报告真实性：** 按要求原文核对报告与实际文件。若要求仅是如实统计实际输出，数据计算错误但报告计数准确时，两项可以一项 violated、一项 satisfied；不能自动联动。
- **观察不足：** 只使用包中实际提供的快照和事件，不能引用被隐藏的历史，也不能把规则分析器的推断当工具事件。

## 五、证据引用格式

只引用实际存在的目录键：

| 引用 | 含义 | 注意 |
| --- | --- | --- |
| `request` | 公开请求及其要求 | 通常需与具体观察证据共同使用 |
| `input:<路径>` | 原始输入，例如 `input:input/data.json` | 前一个 input 是引用前缀，后面是完整原始路径 |
| `file:<路径>` | 当前快照中存在的文件 | 不存在的文件不能作为 file 引用 |
| `snapshot_paths` | 当前完整快照的文件路径清单 | 可与 request 支持必需文件缺失 |
| `event:<索引>` | 可见事件的 index | 使用实际 index，不凭行号猜测；历史 null 时禁止引用 |

`satisfied` / `violated` 必须有非空证据列表；`unknown` 可以为空。有帮助的可见证据也可用于解释 unknown。引用不得重复，不能创造 `observation:files:...` 等格式。

引用存在只是格式合格；人还必须判断它是否真正支持该状态。建议最少引用足以支持结论的证据，不把所有文件无差别粘贴进去，以免产生无意义的证据分歧。

## 六、填写与交付格式

使用 UTF-8 无 BOM 的 JSONL，一行一个完整 JSON 对象。不要把整个文件改成 JSON 数组。只修改模板已有字段，不增删要求，不把说明文字放进 JSON 行中。

以下是**空白结构演示，不是任何案例的标注答案**：

```json
{"case_id":"DEMO-DO-NOT-SUBMIT","reviewer":"","human_verified":false,"findings":[{"id":"R_INPUT","status":"","evidence":[]},{"id":"R_ORDER","status":"","evidence":[]},{"id":"R_RESULT","status":"","evidence":[]},{"id":"R_REPORT","status":"","evidence":[]}]}
```

必须保留实际模板的 case_id 和要求 ID。status 只能填写上述三个英文值。human_verified 是 JSON 布尔值，不能填字符串 `"true"`。未完成人工检查的记录保持 false，不能提交成已审核数据。

自由说明单独写入 `notes.md`，按 case_id / 要求 ID 记录理由、歧义、耗时和核算方式；review 记录只允许 `case_id`、`reviewer`、`human_verified`、`findings` 四个顶层字段，不能自行加 reason 或 confidence。

A/B 独立提交后，协调人保存不可覆盖的原件及提交时间，再进行比较。格式退回只修对应问题，保留原版及修订版；未锁定前不向一人透露另一人的答案。

## 七、协调人合并和检查

**重要：** 发给人的 `packet/cases.jsonl` 只含 case_id/public，不含分组来源元数据，不能直接交给正式数据 CLI。协调人应使用其上一级的完整 `annotation/cases.jsonl`，通过同一个 case_id 对应两份 review。不要把来源字段补进标注者收到的文件。

下面以当前 8 例开发包为例，在仓库根目录操作。将两份真实人员文件放到新的 `runs/annotation/batch-001/`；该目录及文件只作示意，不能用程序自动生成两位人员的判断。

合并示例是 Python，可保存后运行；它只校验、拼接人工原件，不生成或改写标签：

```python
from pathlib import Path
from intentlab.formal_data import read_jsonl, index_reviews, write_jsonl

batch = Path("runs/annotation/batch-001")
cases = read_jsonl("examples/results/formal-m1d-development/annotation/cases.jsonl")
reviews = read_jsonl(batch / "reviews-A.jsonl") + read_jsonl(batch / "reviews-B.jsonl")
index_reviews(cases, reviews)  # 检查每例恰有两名不同且已确认人工审核的人员
destination = batch / "reviews.jsonl"
if destination.exists():
    raise FileExistsError("保留旧合并文件，改用新批次或版本")
write_jsonl(destination, reviews)
```

错误必须先修复：缺案例、重复 case_id/reviewer、未填 true、漏要求、无效状态、引用不存在、已知判断无证据等。程序通过后，协调人仍须检查真实人员和证据语义，不把格式校验当内容质量保证。

生成分歧包：

```bash
python -m intentlab.formal_data conflicts --cases examples/results/formal-m1d-development/annotation/cases.jsonl --reviews runs/annotation/batch-001/reviews.jsonl --out runs/annotation/batch-001/disputes
```

工具比较状态及证据集合：**状态相同但证据集合不同，也会进入仲裁**；仅列表顺序不同不会构成证据分歧。输出目录须不存在。

## 八、第三人仲裁

1. 将 `disagreements.jsonl`、独立的 `adjudication-template.jsonl` 和同版指南交给 C；不提供模型或 oracle 标签。
2. C 先核验公开案例，再分析两人的分歧。裁决可与两位初审人都不同，不用多数表决替代证据。
3. 只处理工具列出的分歧案例，但每个分歧案例必须填写**全部要求**，不只填写发生分歧的一项。
4. 填写稳定的 adjudicator ID、非空 reason、完整 findings；真实核验完成后填写布尔 human_verified=true。reason 应说明关键事实和证据依据，不只写“同意 A”。
5. 保存为 `adjudications.jsonl`。不得由 A/B 自己仲裁同一案例，也不要对原本完全一致的案例额外生成裁决来覆盖标签。

仲裁记录允许的顶层字段为 `case_id`、`adjudicator`、`human_verified`、`reason`、`findings`。若材料本身有缺陷、无法裁决，交协调人修订版本或明确证据不足，不能强行制造确定答案。

## 九、导出、质量复核与归档

存在分歧并已完成仲裁时：

```bash
python -m intentlab.formal_data export --cases examples/results/formal-m1d-development/annotation/cases.jsonl --reviews runs/annotation/batch-001/reviews.jsonl --adjudications runs/annotation/batch-001/adjudications.jsonl --out runs/annotation/batch-001/reviewed
```

**没有任何分歧时，省略 `--adjudications` 参数。** 不要传入空仲裁文件。存在未解决分歧、身份冲突或多余仲裁时，导出会拒绝；不要绕过检查。

导出后核对：

- 案例、要求和两位初审的覆盖完整；每项分歧都有独立第三人裁决及理由。
- 检查原始状态一致率、分歧类型和类别分布。原始一致率应在仲裁前计算，不将仲裁后全部一致冒充初审一致。
- 工具在同一对人员且统计可定义时报告 Cohen's kappa；更换人员组合或退化分布可能返回 null，不能填成 1。高一致率也不保证标签正确。
- 初批建议协调人全量复核证据语义；扩大批量后先登记抽检规则。质量不足时修订指南、培训、返工受影响批次，不根据模型成绩挑选“好”标签。
- 保存原始 cases、两份原件、合并文件、notes、分歧包、仲裁、导出 manifest、版本与 SHA256、交付及修订记录。不要覆盖历史；身份真实信息映射不放进公开数据包。

正式质量阈值和抽样规则应在正式协议中预先登记，不将任意一致率阈值称为质量保证。标注耗时先记录试标实测，再按“案例数 × 单例耗时 + 复核/仲裁”估算，不按要求数虚报独立样本数量。

## 十、交付验收与研究边界

每批交付：两份独立初审文件、notes、必要的仲裁文件、质量统计、完整导出 manifest 和协调人的批次核验记录。只有真实人员完成后，才能更新人工审核完成数。

正式数据还须完成来源及授权核验、要求完整性审核、按源任务/模板隔离、近重复审查、开发功效与预算计划和测试封存。工具导出的 `protocol_frozen=false` 不等于正式协议已冻结。

训练与验证材料可以导出到各自文件；正式 test/OOD 的输入和 gold 分开放置并按角色控制访问。两位审核者为核验标签需要看到公开案例，但训练、提示调参和学习率选择人员不能据正式测试标签调参。正式确认性评估结束前，不公开隔离测试题及答案。

本说明提供执行流程，不代表已有人员、已完成人工审核或正式 M2/M3 验收。当前 8 例包的状态仍是“等待人员确定和真实提交”。
