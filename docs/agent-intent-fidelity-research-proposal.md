# 面向多步骤 Agent 的用户要求保真与证据驱动纠偏：研究建议报告

日期：2026-10-20

适用阶段：课题定位、先导实验与方法设计

来源：用户提供的《思路概括.pdf》（4 页）及围绕该思路的研究分析。原始 PDF 未随本报告上传。

## 摘要

原始思路提出在用户与 Agent 之间建立需求解析、执行追踪、偏差检查和反馈修正闭环，将自然语言要求转化为可追踪的完整要求，并依据工具记录和交付物判断其落实情况。

本报告认为，该方向具有研究价值，但“解析要求、增加检查器、提供反馈”的系统组合不足以独立构成研究贡献。建议将研究聚焦为：**当解析器、执行器和检查器都可能犯错时，如何通过执行证据和修复后的复检，减少约束违反，同时避免纠偏破坏已经满足的要求？**

优先以“纠偏的净收益”为方法主线，以“错误要求在闭环中的传播”为诊断主线。先在可重置、可程序验证的文件与结构化数据处理环境中开展小规模实验，再扩展至代码和多轮工具任务。

本文的方案、优先级和假设属于研究建议，尚无本项目的实验结果支持。相关文献核查为初步定位，不构成穷尽性综述，也不能据此宣称某个方向尚无已有工作。

## 1. 研究对象与边界

### 1.1 对“用户意图”的操作性定义

第一阶段将用户意图限定为**用户明确表达的要求及后续有效澄清**。不将未表达的心理偏好作为评估真值，不声称系统能够完整恢复用户的真实意图。

研究对象包括：

- 任务目标：需要完成什么。
- 硬约束与禁止事项：不得覆盖输入、不得调用某工具等。
- 条件要求：满足特定条件时执行、停止或切换流程。
- 时序与过程要求：先检查再写入、执行前备份等。
- 交付要求：字段、格式、统计信息及证据。
- 一般偏好：在不违反硬约束的前提下优化的属性。

用户原始请求和后续修订是要求来源；工具返回、网页和附件中的文字不能未经来源与权限判断就提升为用户指令。

### 1.2 原始思路中应保留的设计

1. 以包含动作、对象、否定、条件和范围的完整要求作为检查单位。
2. 保留要求的原文出处、适用范围和验证方式。
3. 依据真实执行证据判断，不能把执行器的自我声明当作落实证明。
4. 硬约束违反单独报告，不能被其他要求的高分抵消。
5. 将证据不足标记为待判定，不能默认满足。
6. 检查器始终可以访问原始请求，避免只围绕错误的解析结果闭环。

关键词、词频、历史权重可以作为实现辅助，但不宜作为第一阶段的核心研究主张。低频不代表低重要性，提到某项要求也不代表执行时遵守了它。

## 3. 候选研究问题与优先级

| 编号 | 研究问题 | 研究意义 | 建议顺序 |
| --- | --- | --- | --- |
| RQ1 | 错误的要求解析如何在执行与检查闭环中传播？ | 区分规格错误、检查错误与执行错误 | 作为核心诊断 |
| RQ2 | 怎样修复违规而不破坏已经满足的要求？ | 从局部纠错转向可验证的净收益 | 第一阶段方法主线 |
| RQ3 | 证据不足时，检查器能否可靠地保持待判定并补充验证？ | 避免没有依据的“已满足”结论 | 纳入基础评估，后续深化 |
| RQ4 | 有限检查预算应该分配给哪些要求和步骤？ | 研究收益、风险与成本的关系 | 核心机制有效后扩展 |

### 3.1 RQ1：执行器与检查器的共同盲点

**问题。** 如果解析器遗漏否定、条件或作用范围，执行器和检查器是否会共同认可一个不符合用户要求的结果？仅让检查器读取原文，是否足以消除这种问题？

例如，用户要求“去重并保留每个客户最早的一条，原始文件不得覆盖”，解析结果却只有“去重并保存”。后续执行即使完全符合清单，也可能违反原始要求。

需要同时考察两类错误：

- 约束不足：遗漏或弱化要求，放过违规行为。
- 约束过强：添加用户未提出的限制，阻止合法行为。

**诊断实验。** 交叉替换要求来源与检查来源：

| 要求来源 | 检查来源 | 诊断目标 |
| --- | --- | --- |
| 模型解析 | 模型检查 | 实际系统表现 |
| 人工核验的要求 | 模型检查 | 解析环节的瓶颈 |
| 模型解析 | 基于原始标注的标准检查器 | 独立检查能够挽回多少遗漏 |
| 人工核验的要求 | 标准检查器 | 在正确要求和反馈下的执行、修复能力 |

标准检查器必须依据完整原始标注，不能仅检查模型抽取到的要求。上述替换属于诊断条件，不应作为可部署方法的实际能力报告。

再注入可控的解析错误：漏项、否定翻转、条件缺失、范围错误和优先级错误。比较检查器只读清单、读取清单与原文、从原文独立抽取后交叉核对三种方式。

**证据要求。** 自然产生的错误用于估计实际表现；人工注入错误用于识别机制。两者分开报告，不能用注入实验估计真实错误发生率。

### 3.2 RQ2：避免纠偏引发要求退化

**问题。** 修复一项违规后，是否引入新的违规？如何让反馈与复检机制获得稳定净收益？

例如，为满足 JSON 格式删除必需字段；为修复测试修改要求保留的接口；为减少输出长度省略用户要求的统计信息。

**候选机制。** 每条反馈包含违规要求、执行证据、建议修改对象，以及可能受影响的已满足要求。候选修复生成后，重新检查目标要求与受影响要求；若发现退化，则拒绝该候选修复，在剩余预算内继续尝试。

第一版可以直接复检全部可程序验证要求，不必立即开发复杂的依赖图。待其有效后，再研究受影响范围预测，以减少检查成本。

**隔离反馈作用的实验。** 固定同一出错后的环境快照，比较：

1. 泛化反馈：“请检查并修正”。
2. 具体违规要求。
3. 违规要求加执行证据。
4. 违规要求、执行证据及保持条件。

该实验用于分析反馈内容的作用，随后必须进行完整在线任务实验，检验其是否改善最终表现。快照任务不能全部由单一基线的失败构成，否则可能偏向特定错误分布。

**可证伪假设。** 带保持条件和修复后复检的机制，在相同预算下提高任务成功且全程遵守硬约束的比例。如果局部修复率提高但最终成功率下降，则当前设计未得到支持。

### 3.3 RQ3：证据不足与错误放心

**问题。** 检查器能否区分满足、违反和证据不足？追加验证是否比立即修正更有效？

**实验。** 保持实际执行轨迹和真实结果不变，仅改变检查器可见的信息：最终回复、自我总结、真实工具记录、工具记录加环境状态差异与交付物。进一步加入日志截断、工具失败后声称成功、缺失返回值等条件。

测量违规检出率、误报率、漏报率，以及将证据不足或真实违规判为满足的情况。报告待判定比例和追加验证成本，避免系统通过大量弃判获得表面的高准确率。

若比较同模型和不同模型检查器，需控制成本，并测量共同漏检；不能预设更换模型天然消除共同盲点。

### 3.4 RQ4：预算约束下的检查调度

**问题。** 相同总预算下，固定频率检查、每步检查、随机检查和风险触发检查，哪一种更有效？

可用的风险信号包括即将覆盖文件、调用不可撤销工具、进入条件分支以及环境状态发生变化。要求的重要性不等于检查频率，低检查优先级不能使硬约束失效。

比较任务成功率、违规率与总成本构成的曲线。执行前阻断和执行后修复按操作可逆性分层分析：不可逆违规不能因为最终交付被修正而记为全程合规。

## 4. 推荐课题与系统原型

### 4.1 推荐题目

**面向多步骤 Agent 的证据驱动纠偏：约束修复与已满足要求的保持**

该题目是暂定的工作标题，正式命名应在方法与实验结果明确后调整。

### 4.2 核心假设

在相同资源预算下，携带执行证据与保持条件的针对性纠偏，相比简单重申要求和一般自检，能够提高“任务完成且全程无硬约束违反”的运行比例，其收益不是仅由额外模型调用带来。

### 4.3 最小系统组成

```text
原始请求及有效修订
        |
        v
要求解析：原文、语义、类型、条件、验证方式
        |
        v
Agent 规划与执行 <-------------------------+
        |                                 |
        v                                 |
工具记录、环境变化、交付物                 |
        |                                 |
        v                                 |
证据检查：满足 / 违反 / 待判定             |
        |                                 |
        v                                 |
定位违规及受影响要求 -> 针对性反馈 -> 候选修复
                                          |
                                          v
                                 修复后复检与接受判断
```

硬约束中可执行前验证的部分，在动作提交前检查。对涉及全程行为的禁止要求，应记录历史违反状态，后续修复不能抹除该记录。

### 4.4 要求与反馈的建议字段

| 对象 | 建议字段 |
| --- | --- |
| 要求 | ID、原文出处、语义描述、类型、适用条件、有效版本、验证方式 |
| 检查结果 | 要求 ID、检查时点、判定、证据引用、证据充分性 |
| 纠偏反馈 | 违规要求、证据、建议修改对象、保持条件、复检范围 |
| 修复记录 | 修复前后状态、新增满足项、新增违反项、接受或拒绝、成本 |

对持续性约束，“当前满足”仅表示截至当前未发现违反，不能提前声称未来全程满足。条件尚未触发、当前不适用和证据不足应分别记录。

## 5. 实验设计

### 5.1 第一阶段环境

优先选择本地文件与结构化数据处理，提供可重置沙箱、受控工具、环境快照、动作记录和隐藏评估器。主任务必须需要真正执行，不能仅靠在最终回复中声称完成。

示例任务：

> 合并两份客户表，按客户编号去重并保留最早记录；不得覆盖输入文件；先检查字段是否齐全，缺字段则停止合并并报告；最终报告输入行数、输出行数和去重数量。

验证可以包括输入文件哈希、预期去重结果、输出路径、工具顺序，以及报告统计与实际数据是否一致。检查器应核验语义结果，不能通过关键词命中替代。

### 5.2 任务构造与切分

建议任务族包括合并去重、条件筛选、数据校验、文件转换、分组统计和多文件交付。每个任务均保存自然语言请求、环境初态、人工核验要求、隐藏检查器与预期合法行为。

对基础任务构造单因素或小规模因子变体：

- 关键限制只出现一次或重复出现。
- 要求位于开头、中间或末尾。
- 条件触发或不触发。
- 工具成功或失败。
- 要求相互独立或修复时存在依赖。
- 在相同核心任务中增加无关信息或延迟要求生效的步骤。

不要同时改变任务长度与核心推理难度。训练或开发集与测试集按基础模板或任务族切分，同一模板的改写不能跨集合泄漏。由模型生成的任务和标注须独立审核，不能由同一个模型独自生成、评判并确认真值。

### 5.3 先导实验规模

先使用 **40 个任务、4 个实验组、每组重复 2 次，共 320 次运行**，用于检查任务有效性、错误类型和初步效应。

该规模不是经过功效分析的充分样本量。正式实验根据先导方差、期望检测的最小效应和资源预算确定规模，并扩大任务族与模型覆盖。先导任务若用于反复修改方法，应保留新的独立测试任务。

### 5.4 主实验组

| 组别 | 设置 | 用途 |
| --- | --- | --- |
| A | 原始 Agent，可使用同等额外预算继续执行或自检 | 排除仅由更多计算带来的收益 |
| B | 在关键步骤重申原始要求 | 检验简单提醒是否已足够 |
| C | 要求清单、执行追踪与证据反馈 | 检验结构化闭环的收益 |
| D | C 加保持条件与修复后复检 | 检验减少修复退化的收益 |

关键步骤的定义须预先固定，不能事后选择有利于某组的检查时点。B 组重申产生的输入 token 同样计入成本。D 组额外检查应消耗其自身预算，不能免费获得额外计算。

先导阶段采用这四组；正式实验再加入适用的已有方法与以下消融：去掉证据、去掉保持条件、去掉修复后复检、用原始轨迹替代结构化反馈。

### 5.5 预算公平性

固定模型版本、工具权限、环境和解码设置，预先设定总资源上限。要求解析、检查、反馈和候选修复都计入总成本。

选择清晰的主要预算口径，例如同模型总 token 上限，并设置相同工具调用与运行时上限；记录实际消耗、超时及预算耗尽。涉及不同模型时增加统一价格口径下的费用比较。无法同时完全匹配 token、调用次数与延迟时，应明确主要约束，并提供多个预算档位的结果。

诊断实验中的人工正确要求或标准检查器单独标识，不能与实际方法混合宣称部署性能。

## 6. 指标与统计分析

### 6.1 主指标

**合规任务成功率 = 完成任务且全程无硬约束违反的运行数 / 全部运行数。**

违规以实际环境行为为准。被系统正确阻断的违规提议与实际发生的违规分别记录；阻断后没有完成任务也不能记为任务成功。

### 6.2 辅助指标

| 指标 | 说明 |
| --- | --- |
| 任务完成率 | 独立于约束遵循，衡量主要任务是否完成 |
| 运行级硬约束违反率 | 至少发生一次真实硬约束违反的运行比例 |
| 要求满足率 | 按固定真值要求集合逐项计算，另报全项满足率 |
| 修复成功率 | 修复前违反、修复后满足的目标要求比例 |
| 修复退化率 | 修复前满足、修复后违反的有效要求比例 |
| 检查器质量 | 违规检出、误报、漏报及待判定情况 |
| 检测延迟 | 实际违规或可检测风险出现到被识别的间隔 |
| 成本 | 输入输出 token、模型调用、工具调用、费用及延迟 |

在前后均有效且可比较的要求集合上，记录：

```text
净修复数 = 被修好的要求数 - 被破坏的原已满足要求数
```

同时报告两个分量及其分母，避免净值掩盖大量反复修改。明确区分当前交付状态的改善与全程禁止事项的历史违反。

### 6.3 原始偏差分数的使用建议

原始思路的加权偏差可作为辅助指标：

```text
L = sum(w_i * v_i) / sum(w_i)
```

其中要求集合、权重和违反程度的判定规则由评估方预先确定，不能由被测系统临时决定。硬约束违反仍须单独报告；未判定项不能默认满足，应报告评估覆盖率和必要的上下界。

残余偏差比值 `L_after / L_before` 在初始偏差为零时不定义，接近零时不稳定，应同时报告绝对变化。该分数首先是评估信号，不意味着存在可直接反向传播的训练目标。

### 6.4 独立评价与统计

- 优先使用不向被测系统开放的程序检查器与环境状态真值。
- 系统生成的检查代码不能同时作为最终权威裁判。
- 必须使用语义判断时，对照组信息隐藏，进行独立标注与分歧裁决。
- 对同一任务采用配对比较；置信区间按基础任务或模板聚类，重复运行和文本改写不作为完全独立样本。
- 先确定主比较和主指标；探索性子组结果明确标识，避免只报告有利条件。

## 7. 执行顺序与决策标准

| 阶段 | 主要工作 | 交付物与判断 |
| --- | --- | --- |
| 1 | 核查相邻工作，明确任务、约束与预算 | 文献对照表、实验协议 |
| 2 | 建立可重置环境与独立评估 | 任务集、工具日志、隐藏验证器 |
| 3 | 完成 320 次先导运行 | 错误分布、成本和初步效应 |
| 4 | 开展反馈隔离与解析错误诊断 | 各机制收益及瓶颈证据 |
| 5 | 冻结方法与指标，扩展独立测试 | 跨任务、跨模型与预算曲线 |

结果解释原则：

- D 优于 C：支持保持条件与修复后复检的增益，但还需消融区分二者。
- C 优于 B：支持结构化证据闭环相对简单提醒的增益。
- B 与 D 相当：简化方法或缩小主张，不将系统复杂度当作贡献。
- 人工正确要求显著提高表现：优先解决要求解析保真。
- 检查准确但修复失败：瓶颈更可能在修复或执行能力。
- 违规减少但任务大量停滞：需解决过度阻断，不能只强调违规率下降。
- 收益仅在更高预算出现：转向成本效益结论，不宣称机制在同预算下更优。

## 8. 主要风险与控制措施

| 风险 | 控制措施 |
| --- | --- |
| 将系统集成误当新颖贡献 | 围绕单一可证伪假设，加入简单强基线和已有方法 |
| 解析器与检查器共同漏项 | 保留原文访问、独立真值与解析替换诊断 |
| 检查器误判导致正确结果被修改 | 衡量误报与退化，比较待判定及追加验证策略 |
| 持续禁止要求在最终结果中被掩盖 | 保存不可抹除的历史违规记录 |
| 只在容易验证的合成任务上有效 | 分层扩展真实任务、语义约束与不同模型 |
| 靠频繁检查或停机获得低违规率 | 同时报告合规任务成功率和资源成本 |
| 要求变更与修复退化混淆 | 第一阶段固定要求；动态修订单独建组并标注有效版本 |

## 9. 结论

建议以“证据驱动纠偏能否获得稳定净收益”为首个研究主张，并通过要求解析、检查和执行的分离诊断解释收益来源。第一阶段不必引入复杂赋权、关键词库、强化学习或多个检查 Agent。

最重要的研究产出应是：在独立执行证据支持下，说明纠偏何时有效、何时造成退化、瓶颈位于哪个环节，以及这些结论是否在相同预算下成立。若最终只证明简单提醒已经足够，或检查器错误是主要瓶颈，也应如实报告并据此调整方向。
